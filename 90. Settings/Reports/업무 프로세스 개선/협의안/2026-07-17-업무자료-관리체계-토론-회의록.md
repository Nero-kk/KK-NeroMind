# 업무자료 관리체계 토론 회의록

## 1. 개요

- **일시**: 2026-07-17
- **참석**: 연이(작성), Claude
- **주제**: 업무 프로세스에서 발생하는 자료의 관리 방식 — 폴더 구조·분류 기준, Obsidian 및 타 도구 연동
- **진행 방식**: 포지션 페이퍼 교환 → 상호 반박 → 합의
  - 입장 A(구조·완결성 관점): 유형 전수 분류와 필수 필드로 누락을 '체크 가능한 상태'로 만든다
  - 입장 B(단순·실행성 관점): 사람이 지킬 수 있는 최소 규칙만 남기고 나머지는 링크·검색·자동화가 담당한다
- **판단 기준(3대 최우선 목적)**: ①업무를 체계적으로 진행한다 ②자료를 체계적으로 관리해 실수와 누락을 줄인다 ③업무 경험을 검증 가능한 설계지식으로 바꿔 설계능력을 향상한다. 도구·자동화·문서 수를 늘리는 것은 목적이 아니며, 모든 쟁점은 이 3목적 기여 여부로 판정했다.
- **전제**: 기존 합의(기록 강도 차등, 변경수신검증 4블록, 정본 분리, /wrap 하루마감, 주 1건 지식 검증)는 변경 대상이 아니며, 이번 토론은 그 위에 '자료 관리' 축을 구체화한다.

## 2. 쟁점별 기록

### 쟁점 1. 폴더 수와 분류 축

- **A측**: 자료 유형 전수 분류표(8유형)와 유형별 폴더(00_Inbox/10_Daily/20_Projects/30_Cases/40_Standards/90_Templates, 2단 상한)가 필요하다. 정본 위치가 한 곳으로 정의되어야 "그 자리에 없으면 누락"이 성립한다.
- **B측**: 폴더는 늘리는 순간 실패한다. 저장할 때마다 N지선다 시험이 된다. 분류는 폴더가 아니라 Hub 링크+검색이 담당한다 — "Hub에 링크 1줄 = 분류 완료". 링크는 다차원(프로젝트×부품×Case)이고 프로젝트 종료 후 이사도 불필요하다. 신규 폴더는 Inbox 1개만, 총 6개 상한.
- **반박 요지**: A→B "링크만으로는 정본이 어디인지 정의되지 않는다. 정의 없는 검색은 누락을 못 잡는다." B→A "오분류는 검색으로 찾지만 미기록은 찾을 수 없다. 폴더 정밀도는 미기록을 못 막는다."
- **합의**: 두 주장은 층위가 다르다는 데 동의. **분류표(정본 위치 정의)는 A안 채택, 실행(소속 판정)은 B안의 Hub 링크 채택.** 폴더는 기존 숫자 프리픽스 재사용 + 신규 Inbox 1개, 총 7개(References 선택 포함)·2단 상한. 주간 백링크 0 노트 검색으로 누락 전수 점검. → 목적2(누락의 체크 가능화)와 목적1(저장 고민 제거)을 동시에 충족.

### 쟁점 2. frontmatter 필드 수와 기입 주체

- **A측**: 5필드(project, part_no, rev_seen, sourceRef, status)는 '역추적 보험'. 6개월 뒤 "왜 그렇게 판정했지?"에 5분 내 답하려면 필수. 원본→판정→조치 링크 체인은 사람 성실성이 아니라 템플릿 필수 필드가 보장해야 한다.
- **B측**: 사람 수기 필드는 반드시 미기입이 발생한다. frontmatter 확장은 연이가 자동 기입한다는 전제에서만 수용. 사람 수기 필드 추가는 불가.
- **반박 요지**: B→A "필드가 5개여도 사람이 채우면 60% 규칙이 된다." A→B "자동이면 개수는 문제가 아니다. 단 sourceRef는 절대 양보 불가."
- **합의**: **5필드(project/type/status/rev_seen/sourceRef) 전부 연이 자동 기입, 사람은 rev_seen 값의 사실 확인만 책임.** A의 필드 구성을 B의 자동화 전제로 수용(part_no는 type으로 대체, 부품 소속은 Hub 링크가 담당). → 목적3(역추적 가능한 지식화)에 기여하되 사람 부담 0에 수렴.

### 쟁점 3. 명명 규칙 엄격도

- **A측**: 노트 `{유형}_{프로젝트코드}_{대상}_{YYYYMMDD}`, 서버 파일 `{품번}_Rev{X}_{용도}_{YYYYMMDD}`. 이름만 보고 내용·시점을 알 수 있어야 한다.
- **B측**: 사람이 외울 규칙은 3개 상한. 노트명은 `{프로젝트코드}_{주제}`로 충분 — 날짜는 frontmatter에 있고 연이가 넣는다. 긴 명명 규칙은 지켜지지 않는다.
- **반박 요지**: B→A "노트명 4토막 규칙은 저장 시 마찰이다." A→B "서버 파일만큼은 공유 자산이라 느슨하면 안 된다."
- **합의**: **이원화.** vault 노트 = `{프로젝트코드}_{유형}_{주제}`(날짜는 frontmatter, 연이 생성 — B 기조에 유형 토막만 A에서 수용), 파일서버 업로드분 = 회사 표준 `{품번}_Rev{X}_{용도}_{YYYYMMDD}` 엄격 적용(A안, B도 지지 표명), 보고서류는 기존 관례 `YYYY-MM-DD-제목` 유지. Rev 원칙은 양측 사실상 동일: Rev는 파일명에, 최신 판정은 회사 시스템에, vault는 rev_seen만. → 목적1·2.

### 쟁점 4. 바이너리·사본 보관

- **A측**: 바이너리는 vault 밖, 주소는 vault 안. 경로+Rev+열람일 기록을 강제해야 한다.
- **B측**: 동의하되 포맷은 "정본 참조 한 줄" `[정본] 경로 | Rev | 확인일` — 사람이 책임지는 유일한 한 줄로 최소화. 스크린샷은 판단 근거 스냅샷(증거물)으로 Case에 1장까지 허용, 정본 아님. 고위험 건 한정 판정 시점 PDF를 vault 밖 Evidence/에 동결·읽기전용·Case 링크 3조건부 보관 수용.
- **반박 요지**: 상호 반박보다는 상호 보완으로 진행됨. A→B "동결 사본이 없으면 FAIL 분쟁 시 판정 근거가 사라질 수 있다"에 B가 3조건부로 수용.
- **합의**: **vault 바이너리 반입 금지(.gitignore 차단). 예외 2가지 — ①치수 논점 스크린샷 1장을 Case 증거물로 ②FAIL·분쟁 소지 건 판정 시점 PDF를 vault 밖 Evidence/에 동결(읽기전용·Case에서 링크).** 정본 참조 한 줄 포맷은 B안 채택. → 목적2(분쟁·재추적 대비)와 vault 경량 유지 양립.

### 쟁점 5. 감사 주기와 규칙 강화 방식

- **A측**: Inbox 주 1회 비움·잔류=누락 신호 등 구조 자체에 점검 장치를 심는다.
- **B측**: 분기 1회 30분 구조 감사(백링크 0 노트·Inbox 잔량·깨진 정본 참조) 수용. 단 규칙 추가는 누락률 실측 기반 "증거 기반 강화"만 — 예방 목적 선제 규칙 추가 반대.
- **반박 요지**: A→B "분기만으로는 누락 발견이 늦다." B→A "매주 전수 감사는 지켜지지 않는 의식이 된다."
- **합의**: **이층화.** 주간 5분(백링크 0 노트 + Inbox 잔량 — 기존 금요일 15분 검토에 편입) + 분기 30분(깨진 정본 참조 포함 전수). **규칙 추가는 감사 실측에서 누락이 확인된 항목만.** → 목적2, 유지 비용 최소화.

### 쟁점 6. 태그 체계

- **A측**: 폴더 태그·검색 중심 병행 수용 가능(양보 카드로 제시).
- **B측**: 태그는 TickTick 기존 체계(주 업무 13 + 상황 5) 미러링만. vault 전용 태그 신설 금지 — 같은 개념을 두 어휘로 부르면 검색이 이중화된다.
- **합의**: **B안 채택.** 태그는 TickTick 체계 미러링, vault 전용 태그 신설 금지, 기입은 연이. → 목적1(이중 어휘 방지).

## 3. 양측 양보 사항

| 측 | 양보한 것 |
|---|---|
| A | 필드 수 축소 가능성 제시(단 sourceRef 불가양보 유지), 폴더 대신 링크·검색 중심 병행 수용, 파일서버 구조 개편 포기, 자동화 후순위 수용, 노트명에서 날짜 토막 제거 |
| B | References 폴더 1개 추가 수용(총 7개), 연이 자동 기입 조건으로 rev_seen·sourceRef 등 5필드 수용, 고위험 건 Evidence/ 동결 사본 3조건부 수용, 파일서버 업로드분 회사 표준 명명 엄격 적용 지지, 분기 30분 구조 감사 수용 |

A의 양보 불가 3선(유형별 정본 단일화, sourceRef 필수, rev_seen 기록)은 모두 합의안에 반영되었고, B의 상한 3선(폴더 7개·사람 규칙 3개·수기 기입 최소화)도 모두 유지되었다.

## 4. 합의 사항 총괄

**합의 원칙: "분류는 정본 위치 정의(A)로, 실행은 링크와 자동화(B)로."**

1. 자료 유형 8종 × 정본 위치 단일화 분류표 채택. 기록 강도 차등 합의는 그대로 유지
2. 폴더: 기존 숫자 프리픽스 재사용 + 신규 Inbox 1개. 총 7개·깊이 2단 상한. Inbox 상한 10건·주 1회 비움·잔류=누락 신호
3. 분류: 폴더는 대분류만, 소속 판정은 Hub 링크("Hub에 링크 = 분류 완료"). 주간 백링크 0 노트 검색으로 누락 전수 점검
4. frontmatter 5필드(project/type/status/rev_seen/sourceRef) 전부 연이 자동 기입. 사람은 rev_seen 사실 확인만
5. 사람 규칙 3개 상한: ①정본 참조 한 줄 ②vault에서 Rev 관리 안 함(rev_seen만) ③애매하면 Inbox
6. 명명: vault 노트 `{프로젝트코드}_{유형}_{주제}` / 서버 `{품번}_Rev{X}_{용도}_{YYYYMMDD}` / 보고서 `YYYY-MM-DD-제목`
7. 바이너리 vault 반입 금지(.gitignore 차단). 예외: Case 스크린샷 1장, FAIL 건 Evidence/ 동결 PDF
8. 연동: TickTick=상태 정본(중복 기재 금지, 링크 연결) / Slack sourceRef=체인 시작점(연이 자동 전파) / 이메일은 즉시 Slack 포워딩·첨부는 파일서버 / git 일일 자동 커밋 1회(브랜치·PR 없음) / 태그는 TickTick 미러링
9. 감사: 주간 5분(금요일 검토 편입) + 분기 30분. 규칙 추가는 실측 누락 확인 항목만
10. 파일럿: 실제 업무 3건. 통과 기준 — 잘못된 Rev 참조 0건, 정본 참조 누락 0건, 백링크 0 노트 0건, 수기 기입 건당 평균 3항목 이하. 실패 시 해당 항목만 보강(전면 재설계 금지)

## 6. 비고

이 토론은 원격 세션에서 진행되어 vault 원본 문서를 직접 읽지 못했으며, 스레드에 요약된 기존 합의(기록 강도 차등, 변경수신검증 4블록, 정본 분리, /wrap, 주 1건 지식 검증, TickTick 태그 체계)를 전제로 진행했다. vault 원본과 전제가 다른 부분이 발견되면 파일럿 착수 전에 해당 항목만 재확인한다.
