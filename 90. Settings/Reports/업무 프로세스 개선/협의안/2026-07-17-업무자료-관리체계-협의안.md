# 업무자료 관리체계 협의안

## 1. 요약 (결론 먼저)

**합의 원칙: "분류는 정본 위치 정의로, 실행은 링크와 자동화로."**
자료가 어디에 있어야 하는지는 유형별로 정본을 한 곳으로 못박아 정의하고(구조·완결성 관점), 실제로 그 규칙이 지켜지게 만드는 수단은 폴더 이동이 아니라 Hub 링크·연이의 자동 기입·주기 감사로 한다(단순·실행성 관점).

핵심 결정 5개:

1. **자료 유형 8종 × 정본 위치 단일화 분류표 채택** — 모든 자료는 정본이 정확히 한 곳에만 있다.
2. **vault 폴더는 총 7개·깊이 2단 상한, 신규는 Inbox 1개만** — 분류는 폴더가 아니라 Project Hub 링크가 담당한다.
3. **frontmatter 표준 5필드는 전부 연이가 자동 기입** — 사람은 rev_seen 값의 사실 확인만 책임진다.
4. **사람이 외워서 지킬 규칙은 3개 상한** — ①정본 참조 한 줄 ②vault에서 Rev 관리 안 함 ③애매하면 Inbox.
5. **규칙 추가는 감사 실측에서 누락이 확인된 항목만** — 증거 기반 강화. 파일럿 3건으로 검증 후 정식 운영한다.

이 문서는 「2026-07-17 업무 프로세스 개선 최종 협의안」의 후속으로, 그 합의 중 '자료 관리' 축을 구체화한다. 기존 합의(기록 강도 차등, 변경검증 4블록, 정본 분리, /wrap 하루마감, 주 1건 지식 검증)는 변경하지 않는다.

## 2. 3대 최우선 목적과 판단 기준

이 협의안의 모든 결정은 아래 3대 목적에 종속된다. 도구 수·자동화 수준·문서 수를 늘리는 것은 목적이 아니다.

| 번호 | 목적 | 이 문서에서의 판단 기준 |
|---|---|---|
| 목적1 | 업무를 체계적으로 진행한다 | 자료를 찾는 데 쓰는 시간과 "어디에 둘까" 고민을 줄이는가 |
| 목적2 | 자료를 체계적으로 관리해 실수와 누락을 줄인다 | 누락이 '눈에 보이는 상태'(체크 가능한 상태)가 되는가 |
| 목적3 | 업무 경험을 검증 가능한 설계지식으로 바꾼다 | 6개월 뒤 "왜 그렇게 판정했지?"에 5분 안에 답할 수 있는가 |

아래 각 결정에는 기여하는 목적을 `[목적1]`처럼 표기한다.

## 3. 자료 유형 분류표 `[목적2]`

모든 업무 자료는 아래 8개 유형 중 하나이고, 각 유형의 **정본(원본이자 최신 기준)은 정확히 한 곳**이다. 정본 위치가 하나로 정해져야 "그 자리에 없으면 누락"이라고 기계적으로 판정할 수 있다. 이 표는 '어디에 두는가'의 지도이며, '얼마나 자세히 기록하는가'(기록 강도 차등)는 기존 합의를 그대로 따른다.

| 유형 | 예시 | 정본 위치 | vault 내 흔적 | 보관 |
|---|---|---|---|---|
| A. 요청 원문 | Slack 메시지, 메일 본문 | Slack (메일은 포워딩) | sourceRef 링크만 | Slack 보존 정책 |
| B. 작업 상태 | 할 일, 진행/완료, 마감일 | TickTick | 작업 링크만 (상태 중복 기재 금지) | TickTick |
| C. 도면·CAD·BOM | 3D 모델, 2D 도면, BOM | 회사 파일서버·시스템 | 정본 참조 한 줄 (경로+Rev+확인일) | 회사 규정 |
| D. 판정 기록 | 변경수신검증 결과, FAIL 분석 | MECH_WIKI `30_Cases` | 정본 그 자체 | 영구 |
| E. 일일 로그 | /wrap 하루마감 기록 | MECH_WIKI `10_Daily` | 정본 그 자체 | 영구 |
| F. 검증된 지식 | 설계 기준, Part 등록부 항목 | MECH_WIKI `40_Standards` | 정본 그 자체 | 영구 |
| G. 중간 산출물 | 검토용 임시 계산, 스케치 | 로컬 작업폴더 | 없음 (필요 시 결과만 Case에) | 프로젝트 종료 시 정리 |
| H. 프로젝트 허브 | 프로젝트별 링크 허브 노트 | MECH_WIKI `20_Projects` | 정본 그 자체 | 영구 |

핵심: **vault의 정본은 D·E·F·H(판단과 지식)뿐이다.** 나머지는 vault에 "주소(참조)"만 남긴다. 판단·지식은 vault에, 파일·상태·원문은 각자의 시스템에 — 기존 '정본 분리' 합의의 구체화다.

## 4. 폴더 구조

### 4.1 vault 내부 `[목적1]`

기존 숫자 프리픽스 구조를 재사용하고, 신규 폴더는 `00_Inbox` 1개만 추가한다. **총 7개 상한, 깊이 2단 상한.** 폴더가 늘면 저장할 때마다 N지선다 시험이 되므로, 세부 분류는 폴더가 아니라 Hub 링크가 맡는다(5.1절).

```
MECH_WIKI/
├── 00_Inbox/          # 임시 수신함. 상한 10건, 주 1회 비움. 잔류 = 누락 신호
├── 10_Daily/          # 일일 로그 (유형 E)
├── 20_Projects/       # 프로젝트 허브 (유형 H)
├── 30_Cases/          # 판정 기록 (유형 D)
├── 40_Standards/      # 검증된 지식 + Part 등록부 (유형 F)
├── 50_References/     # (선택) 프로젝트 무소속 참고자료
└── 90_Settings/       # 템플릿·설정·보고서
```

- `00_Inbox`는 "애매하면 여기"의 목적지다. 단, 상한 10건·주 1회 비움을 지키고, 주간 리뷰 시점에 남아 있는 노트는 그 자체가 누락 경보로 취급한다. `[목적2]`
- `50_References`는 선택 폴더다. 프로젝트에 소속시킬 수 없는 자료(범용 규격 요약 등)가 실제로 쌓일 때만 쓴다.

### 4.2 vault 외부 `[목적2]`

```
회사 파일서버/          # 도면·CAD·BOM 정본 (유형 C). 구조 개편하지 않음 — 회사 표준 그대로
로컬 작업폴더/
└── {프로젝트코드}/     # 중간 산출물 (유형 G). 프로젝트 종료 시 정리
Evidence/               # vault 밖. FAIL·분쟁 소지 건의 판정 시점 PDF 동결 보관
└── {프로젝트코드}/     # 읽기전용, 해당 Case 노트에서 링크
```

## 5. 분류·관리 규칙

### 5.1 분류는 Hub 링크로 `[목적1] [목적2]`

폴더는 대분류(유형)까지만 담당한다. "이 노트가 어느 프로젝트·부품·Case에 속하는가"는 **Project Hub 노트에 링크 1줄을 추가하는 것으로 완료**한다.

- 원칙: **"Hub에 링크 = 분류 완료."** 폴더를 더 파고들어 이동시키지 않는다.
- 링크는 다차원이다. 하나의 Case 노트를 프로젝트 Hub와 부품 항목 양쪽에서 링크할 수 있다. 폴더라면 한 곳만 선택해야 하지만 링크는 그럴 필요가 없다.
- 프로젝트가 끝나도 노트를 "이사"시키지 않는다. Hub에 종료 표시만 한다.
- 누락 점검: 주간 리뷰에서 **백링크 0인 노트를 검색**하면 어디에도 연결되지 않은(= 분류 누락) 노트가 전수로 드러난다. "오분류는 검색으로 찾을 수 있지만, 미기록·미연결은 찾을 수 없다"는 원칙에 따라, 점검의 초점은 폴더 위치가 아니라 연결 여부다.

### 5.2 사람이 지킬 규칙 3개 상한 `[목적2]`

사람이 외워서 지켜야 하는 규칙은 아래 3개가 전부이며, 이 상한을 넘기지 않는다. 100% 지켜지는 느슨한 규칙이 60% 지켜지는 엄격한 규칙보다 낫다.

1. **정본 참조 한 줄**: vault 밖 파일을 근거로 판단했다면, 노트에 반드시 한 줄을 남긴다.
   ```
   [정본] \\server\프로젝트X\ABC-1234_RevC_승인도_20260715.pdf | RevC | 확인 2026-07-17
   ```
   이 한 줄이 사람이 사실 여부를 책임지는 유일한 항목이다.
2. **vault에서 Rev를 관리하지 않는다**: 최신 Rev가 무엇인지는 회사 시스템이 답한다. vault에는 "내가 어느 Rev를 보고 판단했는가"(rev_seen)만 남긴다.
3. **애매하면 Inbox**: 어디에 둘지 5초 안에 판단이 안 서면 `00_Inbox`에 넣고 진행한다. 분류 고민으로 업무를 멈추지 않는다.

### 5.3 frontmatter 표준 5필드 `[목적3]`

모든 vault 노트는 아래 5필드를 갖는다. **전부 연이가 접수·작성 시 자동 기입**하며, 사람이 수기로 채우지 않는다. 사람의 책임은 rev_seen 값이 사실인지 확인하는 것뿐이다.

```yaml
project: PJT-X          # 소속 프로젝트 코드
type: case              # 자료 유형 (daily/hub/case/standard/reference)
status: open            # 노트 상태 (open/closed) — 작업 진행 상태 아님(그건 TickTick)
rev_seen: RevC          # 판단 시점에 본 Rev (사람이 사실 확인)
sourceRef: slack://...  # 요청 원문 링크 — 역추적 체인의 시작점
```

- `sourceRef`는 생략 불가다. 원본 요청 → 판정 → 조치로 이어지는 역추적 체인은 사람의 성실성이 아니라 이 필수 필드가 보장한다. 6개월 뒤 "왜 그렇게 판정했지?"에 5분 안에 답하는 보험이다.
- `status`는 노트 자체의 열림/닫힘이며, 작업 진행 상태를 여기 적지 않는다(상태 정본은 TickTick, 6장).

### 5.4 명명 규칙 `[목적1]`

| 대상 | 규칙 | 예시 |
|---|---|---|
| vault 노트 | `{프로젝트코드}_{유형}_{주제}` (날짜는 frontmatter에, 연이가 생성) | `PJT-X_Case_브래킷-홀위치-변경검증` |
| 파일서버 업로드분 | 회사 표준 `{품번}_Rev{X}_{용도}_{YYYYMMDD}` 엄격 적용 | `ABC-1234_RevC_승인도_20260717` |
| 보고서류 | 기존 관례 `YYYY-MM-DD-제목` 유지 | `2026-07-17-업무자료-관리체계-협의안` |

노트명에 날짜를 넣지 않는 이유: 날짜는 frontmatter(`created`)에 이미 있고, 노트명은 검색·링크할 때 사람이 부르는 이름이기 때문이다. 반대로 파일서버는 여러 사람이 공유하므로 회사 표준을 엄격히 지킨다.

### 5.5 Rev 원칙 `[목적2]`

- **Rev는 파일명에, 최신 Rev 판정은 회사 시스템에, vault에는 rev_seen만.**
- 예: 도면 RevC를 보고 간섭 검토를 했다면 → Case 노트 frontmatter에 `rev_seen: RevC`, 본문에 정본 참조 한 줄. 이후 RevD가 나와도 vault를 고치지 않는다. "그때 C를 보고 판단했다"는 사실 자체가 기록의 가치다.
- 변경수신검증 4블록(비교 대상/기본 확인/추가 파급/판정·조치) 템플릿의 '비교 대상' 블록이 rev_seen과 정본 참조 한 줄을 필수로 포함한다 — 기존 합의의 구체화.

## 6. 도구 연동 `[목적1]`

원칙: 각 도구는 자기 정본만 책임지고, 도구 사이는 링크로 잇는다. 자동(연이)과 사람의 경계를 명시한다.

| 도구 | 역할(정본) | 연동 방식 | 자동/사람 |
|---|---|---|---|
| TickTick | 작업 상태 정본 | vault에 상태 중복 기재 금지. 작업↔노트는 링크로 상호 연결 | 링크 생성: 연이 / 상태 갱신: 사람 |
| Slack·연이 | 요청 원문 정본, 단일 진입점 | sourceRef가 역추적 체인의 시작점. 접수 → 실행 카드 → 묶음 승인 → readback 흐름에서 sourceRef 자동 전파 | 자동 |
| 이메일 | 저장소로 쓰지 않음 | 접수 즉시 Slack으로 포워딩(단일 진입점 유지). 첨부 도면은 파일서버로 이동 | 포워딩: 사람(1클릭) / 이후: 자동 |
| git·백업 | vault 이력 보존 | 일일 자동 커밋 1회. 브랜치·PR 없음(1인 지식베이스에 과잉). `.gitignore`로 바이너리 확장자 차단 | 자동 |
| 태그 | 검색 보조 | TickTick 기존 체계(주 업무 13 + 상황 5) 미러링. vault 전용 태그 신설 금지 — 같은 개념을 두 어휘로 부르지 않는다 | 기입: 연이 |

## 7. 감사·검증 루틴 `[목적2] [목적3]`

**증거 기반 강화 원칙: 규칙 추가는 감사 실측에서 누락이 확인된 항목에 대해서만 한다.** 예방 목적의 선제 규칙 추가는 하지 않는다.

| 주기 | 소요 | 점검 항목 | 처리 |
|---|---|---|---|
| 주간 5분 | 기존 금요일 15분 검토에 편입 | ① 백링크 0 노트 검색 ② Inbox 잔량(상한 10건) | 발견 즉시 링크 연결 또는 Inbox 비움 |
| 분기 30분 | 별도 | 전수 점검: 백링크 0 노트, Inbox 누적 추이, **깨진 정본 참조**(서버 경로 이동·파일명 변경) | 누락률 실측 기록 → 반복 누락 항목만 규칙 보강 |

## 8. 파일럿 계획 `[목적1] [목적2] [목적3]`

실제 업무 3건(변경수신검증 포함 권장)으로 이 체계를 검증한 뒤 정식 운영한다. 기존 최종안의 P0 파일럿과 같은 기간에 병행한다.

**통과 기준 (4개 전부 충족):**

1. 잘못된 Rev 참조 0건
2. 정본 참조 누락 0건
3. Hub 백링크 0인 노트 0건
4. 사람 수기 기입 건당 평균 3항목 이하

**실패 시:** 미달한 항목만 보강한다. 전면 재설계는 하지 않는다. (예: 정본 참조 누락 발생 → 해당 템플릿에 필수 블록 추가. 폴더 구조 전체를 다시 짜지 않는다.)

## 9. 하지 않기로 한 것

아래는 검토 후 **의도적으로 하지 않기로** 결정한 항목이다. 3대 목적에 기여하지 않거나, 유지 비용이 이득보다 크다.

| 하지 않는 것 | 이유 |
|---|---|
| vault에 바이너리(도면·CAD·PDF) 반입 | 정본은 파일서버. vault는 판단·지식 전용. `.gitignore`로 차단. 예외 2가지만 허용 — ①치수 논점 스크린샷 1장을 Case에 증거물로 ②FAIL·분쟁 소지 건의 판정 시점 PDF를 vault 밖 `Evidence/`에 동결(읽기전용·Case에서 링크) |
| vault 전용 태그 신설 | TickTick 태그 체계 미러링만. 이중 어휘는 검색을 두 번 하게 만든다 |
| vault에 작업 상태 중복 기재 | 상태 정본은 TickTick 하나. 두 곳에 적으면 반드시 한 곳이 낡는다 |
| git 브랜치·PR 워크플로우 | 1인 지식베이스에 과잉. 일일 자동 커밋 1회로 충분 |
| 회사 파일서버 구조 개편 | 개인이 통제할 수 없는 영역. 업로드분 명명 규칙 준수로 대신한다 |
| 새 도구·서비스 도입 | 현행 4종(Slack·TickTick·Obsidian·파일서버)으로 충분. 도구 추가는 목적이 아니다 |
